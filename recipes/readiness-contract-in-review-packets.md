# Readiness Contract in Review Packets

Use this when a review packet should include repo readiness blockers without embedding a long full scan.

## Goal

Render `repo-flightcheck --contract` output inside a Codex review packet so reviewers see whether the repo is ready for agent work before reading the diff.

## Source Event

This recipe came from updating `codex-review-packet --readiness-report` to accept `repo-flightcheck.agent-contract.v1`.

The public change lets one readiness artifact move through the workflow: generated by `repo-flightcheck`, rendered in the review packet, and imported into `agent-run-ledger`.

## Workflow

1. Generate a readiness contract from the target repo.
2. Build the review packet with that contract passed through `--readiness-report`.
3. Check the packet's `## Repo Readiness` section before reviewing the diff.
4. Treat `Required before agent` items as blockers unless the reviewer explicitly accepts the risk.
5. Attach or import the same contract into a ledger if the handoff needs durable evidence.
6. Regenerate the contract after blockers are resolved.

## Example

```sh
node /path/to/repo-flightcheck/bin/repo-flightcheck.js \
  /path/to/target-repo \
  --contract \
  --threshold 80 \
  > /tmp/repo-readiness-contract.json

python3 /path/to/codex-review-packet/codex_review_packet.py \
  --repo /path/to/target-repo \
  --readiness-report /tmp/repo-readiness-contract.json \
  --output /tmp/review-packet.md
```

Expected packet signal:

```md
## Repo Readiness

- Contract: `repo-flightcheck.agent-contract.v1`
- Ready: `true`
- Score: `100/100`
- Threshold: `80`
```

## Checklist

- Was the contract generated after the current working tree or diff changed?
- Does the packet include `Contract: repo-flightcheck.agent-contract.v1`?
- Are required blockers separated from recommendations?
- Is the threshold visible to the reviewer?
- Is the same contract available for ledger import if the run needs an audit trail?

## Failure Modes

- Rendering a stale contract generated before the diff.
- Hiding readiness blockers in repo context instead of a dedicated section.
- Treating `ready: true` as proof that the code change itself is correct.
- Using a readiness threshold that does not match CI or review policy.
- Letting the packet and ledger import use different readiness artifacts.
